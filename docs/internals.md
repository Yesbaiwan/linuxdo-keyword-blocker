# 实现原理

回答「代码为什么长这样」。这里是全项目**唯一的"为什么"出处**：[constraints.md](constraints.md) 只写"必须怎么做"，理由都在本文。改缓存 / 批处理 / 门控 / 容错前必读。

## 匹配缓存

信息流一屏几十到上百行，每行都要对全部规则判定，而站点还会反复改写行内容，所以判定结果必须缓存。结构是「`topicId` → { 规则版本, 内容指纹, 命中规则 }」（无 `topic-id` 的节点按节点本身做 key）。

三件事决定了它的形态：

- **命中与未命中都要缓存**。骨架期（行插进来但标题、徽章还没填）算出的「不命中」只是一张照片，不是结论，不能当成「这行永远不命中」。
- **靠内容指纹失效，不靠时间**。指纹 = 标题 + 类别 ID 集合 + 标签。三者任一变化就重算，于是骨架期的「不命中」在内容填进来后自动作废，不需要额外的事件通知。
- **整批失效只有两个触发点**：规则变了（`matchVersion` 递增），或缓存条数超 4000（整批丢弃，避免长时间浏览无限累积；重算很便宜）。

不能只存命中，也不能只按 `topicId` 复用——前者会把骨架期的中间态冻结成漏过滤，后者会把标题改过的行沿用旧结论。

## 批量扫描

**为什么要先收集再判定。** 站点不是一次性把一整行插进来的：骨架、标题、徽章分多次进入 DOM。每来一个节点就判定一次，同一行会被反复计算，而且骨架期那几次必然算错。所以 `handleAddedNodes` 先把行收进 Set 去重，批次末尾每行只判定一次。

**为什么要在绘制前同步处理。** 新增行在浏览器绘制前同步落状态，避免「先显示后隐藏」的闪现与跳动。

**为什么文本节点只提升宿主行。** 站点填标题和数字用的是文本节点；文本没有后代，往上找到最外层行就够了，不必查后代。

**为什么不读容器的 `textContent`。** 大容器上读它会遍历整棵子树，代价太高。被顺带触及但内容没变的行，由指纹缓存直接命中，不会白算。

**未挂载节点的处理。** 父链不完整的节点可能被误判成最外层行，所以等它挂载后随子树统一处理。

**嵌套行的处理。** 搜索结果内层也带 `topic-id`，判定前先向上找到最外层行；内层清掉状态（Ember 会回收复用行节点，不清会留下残留）。

## 状态落地时机与设置变更

**全量扫描只在两个时点发生**：初始化，与设置变更。日常浏览全靠观察器增量处理，不做全页重扫。

**设置变更是统一入口**：写存储 → 重算匹配缓存 → 重扫页面（需要重建列表时先复位编辑态），三者绑在一起走，避免出现「存储改了但缓存没失效」这种中间态。

## 交互取舍

**清空确认态换 `title` 提示下一步动作**，而不是在按钮旁挂静态说明：原生 tooltip 有约 1 秒悬停延迟，静态说明在 3 秒的确认窗口内基本看不到，而 `title` 在确认态出现时就能读到。

## 类别树门控

**为什么要有 `ready`。** 类别规则的展示名依赖 `/site.json`（例如「类别:4」在树到位后显示成「类别:开发调优（所有等级）」）。树还没到就落状态，用户会看到页面先按一套名字过滤、树到了再跳一次。

**`ready` 的真实条件不是"树到了"。** 只有「所有等级」规则才需要那棵树（要展开全部后代等级）；没有这类规则时，`ready` 一开始就是 `true`，立刻过滤，首屏不等树。这样避免了为不依赖树的用户白白推迟过滤。

**拉取失败的三层兜底。** ① 缓存优先（7 天）→ ② 未命中则拉取，失败重试 3 次 → ③ 仍失败就标记出来，在面板状态行提示、下拉底部给「点此重试」入口。全程挂起的连接靠超时掐断，走既有的重试 → 降级路径，不会把过滤无限期拖住；降级后已存的类别规则仍按徽章 ID 生效。

**父分类不在可见列表时按顶级展示**（受限或已删除的分类），保证下拉里不丢项。

## 防自我触发与幂等

- **幂等守卫 `__lkcbLoaded`**：同一文档被重复注入（用户装了油猴又手动注入、或注入竞态）会产生双实例，互踩渲染，所以第二次直接不启动。
- **观察器跳过 `lkcb-` 前缀节点**：脚本自己写的 UI 也在被观察的子树里，不跳过就会自我触发、无限循环。

## 容错

**存储形状损坏当"没有"处理。** 手改存储或导入非数组 JSON 时，`for...of` 对非可迭代值会直接抛错，会把 `loadSettings` / 导入整条链路炸掉。所以 `normalizeRules` 先把形状不对的一律当空数组，这一条守卫同时兜住存储读取与导入两条路径。

**规则判重指纹不含 `enabled`。** 同内容但启停状态不同的两条算同一条，保留先出现的。`normalizeRules`（存储/导入）与表单的重复校验共用同一个指纹，保证"重复"的判定处处一致。
